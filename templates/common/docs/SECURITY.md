# 보안 설계

이 프로젝트에 들어 있는 보안 장치가 **무엇을 막고 무엇을 막지 못하는지** 정리한 문서다.
기능을 추가할 때 이 문서의 "기능을 추가할 때 지킬 것"을 먼저 읽는다.

## 1. 원칙

1. **보안 경계는 서버다.** 브라우저로 내려간 코드는 공격자가 읽고 고칠 수 있다. 인가, 입력 검증, 금액·수량 계산 같은 결정은 반드시 백엔드에서 한다.
2. **클라이언트 보호(난독화, 안티 디버깅, 보안 채널의 클라이언트 쪽 코드)는 지연 수단이다.** 분석 비용을 올리고 흔적(신호)을 남기는 것이 목적이다. 이것으로 서버 측 취약점을 가릴 수는 없다.
3. **통제는 테스트로 고정한다.** `scripts\test.bat` 이 변조·재전송·차단 동작을 실제로 확인한다. 보안 관련 코드를 고치면 테스트도 함께 고친다.

## 2. 구조

```
인터넷 ─▶ NPM (TLS 종료, 80/443 만 공개)
            │  edge 네트워크
            └─▶ web  (nginx: 정적 파일 + CSP + /api 프록시 + IP 기준 속도 제한)
                  │  backend 네트워크 (internal: 외부로 나가는 경로 없음)
                  └─▶ api  (__BACKEND_LABEL__: 보안 채널, 검증, SQLite)
```

| 통제 | 위치 |
|---|---|
| TLS, HSTS, 공통 보안 헤더(nosniff 등) | NPM (`docs/DEPLOY.md`) |
| CSP, 정적 파일 캐시, 소스맵 차단, IP 기준 속도·크기 제한 | `frontend/nginx/` |
| Host 검사, Origin 검사, 보안 채널, 입력 검증, 핸드셰이크 제한, 보안 이벤트 기록 | `backend/` |
| 컨테이너 권한 축소(non-root, read-only, cap_drop), 네트워크 분리, 비밀 주입 | `docker-compose.yml` |
| 소스맵 제거, console 제거, 난독화, 번들 점검 | `frontend/` 릴리즈 빌드 |

## 3. 보안 채널 (가로채기 프록시 대응)

브라우저는 인증서 고정(pinning)을 할 수 없으므로, 사용자가 자신의 PC 에 프록시 CA 를 설치하면 TLS 안쪽의 HTTP 가 그대로 보인다(Burp, Fiddler, mitmproxy). 그래서 TLS 위에 한 겹을 더 둔다.

**핸드셰이크** `POST /api/hs`

1. 브라우저가 임시 ECDH(P-256) 키 쌍을 만들어 공개키를 보낸다.
2. 서버가 임시 공개키, salt, 그리고 **장기 서명 키로 만든 서명**(ECDSA)을 돌려준다.
3. 브라우저는 번들에 박힌 서버 공개키로 서명을 검증한다. 프록시가 키 합의에 끼어들면 서명을 만들 수 없어 여기서 실패한다.
4. 양쪽이 공유 비밀에서 HKDF 로 `암호화 키(AES-256-GCM)`와 `서명 키(HMAC-SHA256)`를 유도한다. 브라우저 쪽 키는 추출 불가(non-extractable)로 메모리에만 둔다.
5. 서버는 세션을 만들고 `HttpOnly; Secure; SameSite=Strict` 쿠키로 식별자를 내려 준다.

**요청마다**

| 장치 | 내용 | 막는 것 |
|---|---|---|
| 서명 `X-Sig` | HMAC(메서드, 경로+쿼리, 타임스탬프, nonce, 본문 해시) | 메서드·경로·쿼리·본문 변조 |
| 타임스탬프 `X-Ts` | 서버 시각과 ±30초 이내만 허용 | 오래된 요청 재사용 |
| nonce `X-Nonce` | 같은 값은 한 번만 허용 | 재전송(replay) |
| 본문 암호화 | AES-GCM, AAD 에 메서드·경로·타임스탬프·nonce 포함 | 프록시에서 평문 열람, 다른 요청으로 옮겨 붙이기 |
| 응답 암호화 | AES-GCM, AAD 에 요청 nonce·상태 코드 포함 | 응답 열람·변조, 가짜 성공 응답 주입 |

구현 위치: 백엔드 `security/` (crypto, sessions, middleware), 프론트 `src/security/` (channel.ts, api.ts).

**막지 못하는 것**

- 브라우저 자체를 조작하는 공격자(확장 프로그램, 수정된 브라우저, 번들을 고쳐서 서빙하는 프록시)는 클라이언트 코드를 바꿔 정상 클라이언트처럼 요청을 만들 수 있다. 난독화와 가드가 이 작업을 느리게 할 뿐이다.
- 따라서 **"채널을 통과한 요청 = 정상 사용자의 의도"가 아니다.** 채널을 통과한 요청도 서버에서 검증·인가한다.

**운영상 제약**

- 세션·nonce·속도 제한이 api 프로세스 메모리에 있다. **api 는 인스턴스(워커) 1개**로 운영한다. 늘리려면 먼저 저장소를 Redis 등으로 옮긴다.
- api 가 재시작되면 세션이 사라진다. 브라우저는 401 을 받아 자동으로 다시 핸드셰이크한다. 로그인 상태를 세션에 두었다면 다시 로그인해야 한다.
- 응답을 모아서 암호화하므로 `/api/` 아래에서는 스트리밍 응답(SSE 등)을 쓸 수 없다.
- WebCrypto 는 HTTPS 또는 localhost 에서만 동작한다. 사설 IP 에 HTTP 로 접속하면 채널을 열 수 없다.

## 4. 리버싱 방지

**프론트** (`npm run build:release`, Docker 이미지 빌드 시 자동 실행)

| 단계 | 내용 |
|---|---|
| 빌드 | 소스맵 없음, `console.*` 제거, 라이브러리는 `vendor` 청크로 분리 |
| 난독화 | 앱 코드 청크만 대상. 제어 흐름 평탄화, 문자열 RC4 인코딩, 죽은 코드 삽입, 자기 방어(정리하면 동작 안 함). 옵션: `frontend/obfuscator.config.mjs` |
| 점검 | `scripts/verify-dist.mjs` 가 소스맵·비밀 문자열·console 잔존·평문 식별자를 검사하고, 걸리면 빌드를 실패시킨다 |
| 도메인 잠금(선택) | `.env` 의 `OBF_DOMAIN_LOCK` 을 지정하면 그 도메인에서만 코드가 실행된다 |

CSP(`script-src 'self'`)와 충돌하지 않도록 `eval`/`new Function` 을 쓰는 옵션(`debugProtection` 등)은 끄고, 안티 디버깅은 `src/security/clientGuard.ts` 가 맡는다.

**클라이언트 가드** (운영 빌드에서만 동작)

| 신호 | 탐지 방법 | 기본 처리 |
|---|---|---|
| `devtools-timing` | `debugger` 문에서 멈춘 시간 | 세션 무효화 |
| `debugger-tamper` | `fetch` 등 네이티브 함수 후킹 여부 | 세션 무효화 |
| `devtools-size` | 창 안팎 크기 차이 | 기록만 (오탐이 잦다) |
| `devtools-console`, `automation` | 콘솔 렌더링, 자동화 브라우저 특성 | 기록만 |

- 탐지 → 보안 채널로 서버에 보고 → **서버가** 세션 무효화 여부를 결정 → 화면이 차단 안내로 바뀐다.
- 정책은 `.env` 의 `GUARD_POLICY`(revoke/report), `GUARD_REVOKE_SIGNALS` 로 조정한다. 오탐이 걱정되면 먼저 `report` 로 운영하며 `security_events` 테이블을 살핀다.
- 공격자는 신호를 보내지 않게 코드를 고칠 수 있다. 가드는 결정적 방어가 아니라 비용과 흔적이다.

**백엔드** (이미지가 유출됐을 때 소스가 그대로 읽히지 않게)

- FastAPI: `build_protect.py` 가 `app/security/core` 를 Cython 으로 네이티브 컴파일하고, 나머지는 `.pyc` 만 남긴다. 최종 이미지에 `.py` 소스가 없다. `.pyc` 는 디컴파일 도구로 상당 부분 복원되므로, 보호 가치가 큰 로직은 `CYTHON_PACKAGES` 에 넣는다.
- Rust: release 프로필에서 LTO + 심볼 제거(strip), 빌드 경로 문자열 치환, 셸 없는 distroless 이미지.

## 5. 보안 이벤트

서명 불일치, 재전송, 오래된 타임스탬프, 본문 초과, 핸드셰이크 제한 초과, 가드 신호, 세션 무효화는 로그와 SQLite 의 `security_events` 테이블에 남는다(세션 식별자는 해시 앞부분만). 한 IP 가 기록을 쏟아내 디스크를 채우지 못하도록 DB 기록은 IP 당 분당 60건으로 제한한다.

## 6. 기능을 추가할 때 지킬 것

- **API 호출은 `src/security/api.ts` 의 `api()` 만 쓴다.** `fetch` 를 직접 쓰면 채널을 거치지 않아 서버가 거부한다.
- **요청 스키마는 정의하지 않은 필드를 거부한다.** (FastAPI: `StrictModel` 상속 / Rust: `#[serde(deny_unknown_fields)]`) 문자열 길이·숫자 범위·목록 크기에 상한을 둔다.
- **응답 스키마를 따로 둔다.** DB 모델을 그대로 내보내지 않는다.
- **로그인을 붙일 때**: 비밀번호는 argon2id, 로그인 성공 시 세션 재발급(세션 고정 방지), 실패 횟수 제한(계정+IP 기준), 사용자 식별자는 채널 세션의 `data` 에 저장, 보호할 라우터에 인증 의존성을 라우터 단위로 건다. 사용자별 데이터는 **소유자 조건**을 쿼리에 넣고 남의 객체는 404 로 응답한다.
- **SQL 은 ORM 또는 바인딩 파라미터만 쓴다.**
- **화면에 HTML 을 직접 넣지 않는다.** (`v-html`, `dangerouslySetInnerHTML`, `innerHTML` 금지)
- **번들에 비밀을 넣지 않는다.** `VITE_` 변수와 `define` 값은 전부 공개된다.
- **CSP 를 풀지 않는다.** 외부 리소스가 필요하면 `frontend/nginx/snippets/csp.conf` 에 출처를 정확히 추가한다. `'unsafe-inline'`, `'unsafe-eval'` 은 넣지 않는다. 인라인 `style="..."` 도 CSP 에 걸리므로 클래스를 쓴다.
- **파일 업로드, 외부 URL 요청(SSRF), WebSocket, 결제**는 이 보일러플레이트에 포함돼 있지 않다. 추가할 때 해당 기능의 보안 요구사항을 따로 확인한다.
